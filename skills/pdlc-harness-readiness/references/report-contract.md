# Executive harness brief

Write for a CTO, VPE, or head of AI SDLC/PDLC adoption. The Markdown brief is canonical; a matching self-contained HTML view is preferred when a visual report is requested or useful. Use task-specific filenames under the output workspace, never inside a read-only target. Avoid raw prompt excerpts unless they prove a finding.

## First screen

1. **Verdict and dependable boundary:** “This configuration reliably carries work through …; responsibility for … is …”. Bound the claim to documented support.
2. **Scope:** distribution versus effective installation; input type, revision/date, default/optional route, agent/version/task directory if relevant, coverage and confidence.
3. **Five-axis visual:** five labeled 0–4 horizontal bands (Upstream discovery, Trustworthy delivery, Downstream validation, PDLC integration, Compounding). Show Unknown as unplotted. Label the bands as ordinal, not percentages. Use color and text; no radar chart or total score. A comparison may add the familiar Upstream/Downstream and SDLC/PDLC quadrants, with Compounding displayed as a separate scored rail.
4. **What to keep; first harness move:** two concrete strengths and the highest-impact reusable change, with the decision it supports.

## Detailed read

- **Path map:** entry → discovery/commit → delivery/verification → adoption/review → adaptation; identify the point where responsibility ends. Show required path separately from optional/installed extensions.
- **Axis score table:** band, evidence source, rationale, what would raise it one band, and confidence. The seven-dimension PDLC profile may be compact but must remain visible when scored.
- **Trustworthy-output read:** one realistic failure that current checks would catch, and one they would miss or leave unverified. Cite test/review/convergence instructions; do not infer execution.
- **Compounding read:** distinguish product/feature learning from improving the harness. Identify the capture surface, improvement decision owner, versioned change, verification on later runs, and kill/revert route. State the missing link.
- **Up to three prioritized harness recommendations:** evidence, plausible impact, smallest change to an active path, proposed owner, and acceptance check on a future generated spec/run. Do not prescribe editing a vendor repo when the user has only configured an overlay.
- **Sources and limits:** exact paths/lines or pinned URLs, inspection boundary, missing layers, and any counterevidence. Treat inaccessible files as Unknown.
- **Next decision:** one owner-facing choice and the evidence that would prove the harness improved.

For a multi-framework comparison, keep the first screen compact: one configuration-per-row score matrix, one source-linked rationale per row, a confidence key, and the dominant next-band move. Reserve the full five-axis source/rationale/next-band table for a single-organization assessment. Never blur a documented optional combination into the default row.

The five-axis visual and first recommendation should be understandable in two minutes. Framework marketing, impressive test counts, optional command menus, and agent model quality do not substitute for a connected evidence path. If HTML is produced, inline SVG/CSS, keep source-derived text escaped, and inspect desktop and narrow layouts. Do not publish or modify the assessed harness as part of the assessment.
