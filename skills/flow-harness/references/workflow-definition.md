# Flow Workspace Contract — the Definition of Workflow, machine-readable

The single source of truth for what makes a folder a **flow workspace**. Every
`flow-harness-*` skill and every script in `../scripts/` reads and writes against this
contract. Change it here first; `../templates/` instantiates it.

A flow workspace holds one **value stream** run as an agentic loop: the graph it flows
through, the contract for each step, the items in flight, what we measure, where the work
is mirrored, and the context platform that makes agents useful in it.

## Layout

```
<flow-workspace>/
  AGENTS.md              # thin router: points agents at flow-harness + the run loop
  workflow.md            # THE definition of workflow — narrative + <!-- flow-config --> block
  steps/<step-id>.md     # one contract per step: intent, exit evidence, delegate, run, inner graph
  items/<slug>/item.md   # the work items flowing through the graph (+ whatever they accumulate)
  measures.md            # the measurement plan — what we steer on, and what we refuse to
  integrations.md        # system-of-record bindings + field ownership + sync log
  platform/
    context/<pack>.md    # context packs: the reusable knowledge steps run against
    checks/<check>.md    # verification recipes (independent of the step that did the work)
    prompts/<name>.md    # run refs for steps whose run model is `prompt`
  improvements/<slug>/improvement.md   # meta-loop bets on the workflow itself
  learnings/<slug>.md    # one durable learning per file
  reviews/
    loop-log.md               # one line per loop cycle
    YYYY-MM-DD-<intent>.md    # decision briefs, meta-loop reports, ingest/wiring briefs
  board.md               # GENERATED by scripts/flow_board.py — never hand-edit
  flow-log.csv           # GENERATED append-only transition log — never hand-edit
```

Slugs are kebab-case and permanent; retitle in frontmatter, never rename the folder.
Step ids are kebab-case and short (`draft`, `angle-test`), because they appear in every
edge, every item, and every log row.

## `workflow.md` — the `flow-config` block

The human document explains the workflow; this island makes it executable. Scripts fall
back to nothing — an absent or unparsable block is a lint error, not a default, because a
guessed graph is worse than no graph.

```
<!-- flow-config
id: fiy-content-engine
kind: content                 # development | operational | content | ai-use-case | custom
steps: intake, research, angle-test, draft, edit, publish, amplify, learn
optional_steps: angle-test, amplify
entry: intake
terminal: shipped, dropped
edges:
  intake -> research
  research -> angle-test
  research -> draft            [when: angle already evidenced]
  angle-test -> draft
  angle-test -> dropped        [when: angle fails the audience probe]
  draft -> edit
  edit -> draft                [rework]
  edit -> publish
  publish -> amplify
  publish -> learn
  amplify -> learn
  learn -> intake              [when: a learning spawns a new item]
  learn -> shipped
wip_limits: draft=2, edit=2, publish=1
aging_thresholds: intake=14, research=10, angle-test=7, draft=7, edit=5, publish=3, amplify=10, learn=14
decision_points: publish
evidence_exits: research, angle-test, edit, publish
cadence: daily loop, weekly meta-loop
-->
```

| Key | Meaning |
|---|---|
| `id` | Stable identifier for this stream; used by exports and cross-stream rollups. |
| `kind` | Archetype — routes to a starting point in `workflow-archetypes.md`. Free text is fine. |
| `steps` | Every step id, in **narrative order**. Order is presentation and rework detection only; the edges are the truth. |
| `optional_steps` | Steps that may be skipped — but skipping is a *decision*, recorded on the item, never a default. |
| `entry` | Where new items land. |
| `terminal` | Absorbing states (`shipped`, `dropped`, `frozen`…). Items here are out of flow and out of WIP. |
| `edges` | `from -> to [tag: note]` lines, one per line. The graph — branches, joins, back-edges, and the closing edge of the loop all belong here. |
| `wip_limits` | `step=N`. Absent means unlimited, which is a position, so say it out loud in the narrative. |
| `aging_thresholds` | `step=days`. Item age past the threshold is a flag, not a failure. |
| `decision_points` | Steps an item may only **enter** with a dated human decision in its Decision log. |
| `evidence_exits` | Steps an item may only **leave** with recorded exit evidence (see items, below). |
| `cadence` | Free text: how often the run loop and the meta-loop fire. |

Edge tags in `[...]`: `when: <condition>` documents a branch condition an agent must
evaluate and record; `rework` marks a deliberate return path. Any edge whose target sits
earlier in `steps:` counts as rework whether or not it is tagged.

**Graph, not chain.** A straight line is a legal graph and a fine place to start. Branches,
joins, and back-edges earn their place when the work actually behaves that way — a graph
that lies is worse than a chain that is honest.

## `steps/<step-id>.md` — the step contract

Frontmatter is the machine state; the body is how a human (or an agent) actually runs it.

```yaml
---
id: draft
name: Draft the piece
type: transform          # intake | transform | decision | verify | wait | measure
intent: "Turn the evidenced angle into a publishable draft in our voice"
delegate_rung: 2         # 0–5, see step-contracts.md — the DEFAULT for items in this step
run: prompt              # skill | prompt | script | tool | human | external
run_ref: platform/prompts/draft.md
context_packs: [house-voice, audience-map]
inputs: [research pack, angle evidence]
exit_evidence:
  - "Draft cites at least two named sources from the research pack"
  - "House-voice check run and its findings resolved or waived with a reason"
verify_with: platform/checks/house-voice.md     # independent of the run
escalate_when: "two rework passes without converging, or the angle stops holding"
escalate_to: Yuval
budget: "45 agent-minutes; 20 human-minutes"
measures: [rework-rate, human-minutes-per-item]
inner_graph: true
---
```

Field rules:

- `delegate_rung` is the step's default rung on the delegation ladder (0 human-only →
  5 closed-loop automation). An item may carry `delegate_override` for one pass; a
  *permanent* change is a meta-loop bet, not an edit in passing.
- `run` + `run_ref` answer "how does this step actually get run" — a skill to load, a prompt
  file, a script to execute, a tool/API call, a human activity, or an external system.
  `run: human` with an empty `run_ref` is honest and common at rung 0–1.
- `exit_evidence` is the contract's spine: what you can rely on when an item leaves here.
  Write artifacts and observations, never activities. "Reviewed" is not evidence; "review
  findings recorded on the item, unresolved ones listed" is.
- `verify_with` should name something *other than the runner* — a script beats a second
  agent, a second agent beats the same agent, and the same agent with a fresh context and
  an adversarial prompt beats nothing.
- `inner_graph: true` requires an `## Inner graph` section in the body (below).

Body sections: `## Intent` · `## Exit evidence` (the detail behind the frontmatter, each
line checkable) · `## Inner graph` (the mini-graph, if any) · `## Run contract` (context,
tools, guardrails, stop rule) · `## Delegation & escalation` (why this rung, what would
promote or demote it) · `## Failure modes` (how this step lies to you).

### `## Inner graph` — mini-graphs inside a step

A step whose work has more than one distinct failure mode deserves its own bounded loop:

```
<!-- step-graph
nodes: outline, expand, self-critique, revise, citation-check
entry: outline
edges:
  outline -> expand
  expand -> self-critique
  self-critique -> revise      [when: findings exist]
  self-critique -> citation-check
  revise -> self-critique      [rework]
  citation-check -> exit
max_iterations: 2              # on any rework edge — the stop rule is mandatory
-->
```

Inner graphs are private to the step: items do not sit on inner nodes, the board does not
project them, and the flow log does not record them. They are how the step is run, not
where work waits. Every inner loop carries `max_iterations` or a falsifiable exit — an
unbounded critique-revise loop converges on plausibility, not on truth.

## `items/<slug>/item.md` — the work item

```yaml
---
title: "Why your agentic pipeline is a flow system"
kind: item               # item | rollup | spike
step: draft
step_entered: 2026-08-14
owner: Yuval             # accountable human, whatever the delegate rung
holder: agent            # human | agent | pair | blocked | waiting-decision — who holds it NOW
class: standard          # standard | expedite | fixed-date | derisk-first
outcome_hypothesis: "Practitioners can name the two loops and redraw their own flow"
evidence_exits_met: [intake, research]
parent: q3-agentic-series          # tree/scale — omit for top-level items
children: [piece-one, piece-two]   # rollup only
blocked_by: ""           # non-empty means blocked, and the board says so
next_decision: "2026-08-25 — publish or hold for the launch? (Yuval)"
delegate_override: 1     # optional, one pass only, with a reason in the body
---
```

Field rules:

- `step` must be a known step id or a terminal state; `step_entered` updates on every
  transition — it is what makes age computable.
- `holder` is the honest answer to "who is holding this right now". It is what turns a
  board into a delegation x-ray, and it is the field people are most tempted to fudge.
- `evidence_exits_met` lists step ids whose `exit_evidence` was actually verified and
  recorded in the body. The board cross-checks it against the transition history: leaving
  an `evidence_exits` step without its id here is a contract violation — that is the
  mechanic that stops watermelon steps.
- `parent` / `children` implement expand-collapse (see `scaled-flow-patterns.md`). A
  `rollup`'s own `step` is derived from its children by the board; set it to the entry
  step and let the projection correct you.
- `next_decision` starts with `YYYY-MM-DD` when a date exists — the board reads that prefix
  to flag overdue decisions and the run loop routes to them first.

Body sections: `## Context` · `## Exit evidence log` (dated, per step — the receipts behind
`evidence_exits_met`) · `## Decision log` (dated, naming humans; required to enter a
decision point) · `## Escalations` (what the agent could not settle, and what happened) ·
`## Notes`.

## Generated files

- `board.md` — the projection: per-step columns with WIP vs limit, ages, holders, flags,
  rollups collapsed by default, plus the metric block. Regenerate; edits are lost by design.
- `flow-log.csv` — `date,slug,from_step,to_step` appended by the board script whenever an
  item's `step` differs from its last logged step (transition date = the item's
  `step_entered`). Feeds cycle time, throughput, rework rate, and the meta-loop.

## Invariants

1. **Item frontmatter is the state.** The board, the flow log, and every mirrored tracker
   are projections. Disagreement is a bug in the cycle, not a matter of opinion.
2. **Exactly one writer per field.** `integrations.md` names the owner of every mirrored
   field. Two writers is not a sync problem, it is a design error.
3. **Exit evidence beats status.** A step is finished when its evidence exists, not when a
   run completes without erroring.
4. **Decision points are human.** Entering one without a dated Decision-log entry naming a
   person is a contract violation the scripts flag and the loop must fix before moving on.
5. **The definition of workflow changes deliberately.** Edits to `workflow.md` or a step
   contract need a dated line in the Change log at the bottom of `workflow.md` and, for
   anything beyond a typo, an improvement card that carried the bet.
6. **Nothing here requires a specific harness, tracker, model, or OS.** Plain markdown and
   `python3` stdlib, by design.
